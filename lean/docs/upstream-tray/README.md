# A reader's guide for the linksem developers

This page is for the maintainers of [rems-project/linksem](https://github.com/rems-project/linksem)
who have been pointed at this directory to look at the reports we have
drafted against linksem (and one against Lem). It explains what this
branch is, how the reports came about, how to read one, and what to trust.
The ranked list is [INDEX.md](INDEX.md); the reports are the numbered files
next to it.

## 1. What this branch is

The `lean/` directory of this branch is a Lean 4 build of linksem. The Lean
code is generated from the **same `.lem` sources** as linksem's OCaml
build, by a Lean backend added to Lem in a sibling project (`lem-lean`).
The parts linksem implements directly in OCaml (`src/*_wrapper.ml`,
`src/ml_bindings.ml`, `src/filesystem_wrapper.ml`) are hand-written Lean
twins with the same names, mirroring the OCaml. The work's purpose was to
exercise the Lean backend on a second large Lem development; the reports
here are by-products.

## 2. How the findings arose

- **Differential execution, OCaml vs Lean.** Both builds' `main_elf` run
  over a corpus of 183 ELF files (x86-64, i386, PowerPC64, MIPS64, AArch64,
  linksem's own `test/` binaries) with every flag, and their outputs are
  compared byte for byte. Porting means reading every line of the OCaml helpers
  against the model, and a disagreement between the two builds has to be
  explained, which is where most of these reports come from.
- **Independent oracles.** Where there is one: `readelf`/`objdump`, `gcc`
  and `ld` (for the linker: ld links the same objects, and both executables
  are RUN and their exit statuses compared), or a Python computation.
- **Adversarial fuzzing** of the hand-written helpers (~23,000 cases, one
  auditing pass) found the 2^62 boundary of report 04.
- **Running linked programs.** Report 01 was found by running the
  executables `main_link` writes next to ld's (each test program exits
  with a computed status).

## 3. Our stance toward upstream

The Lean build is meant to compute exactly what linksem's OCaml build
computes, including where we believe linksem is wrong: the port mirrors
upstream. It changes upstream (on both sides, so the OCaml build stays the
reference) only where upstream wrongly models the ELF artifact in a way our
use case exercises, malformed or hostile input included: INDEX.md marks
those "fixed". Everything else here is reported, not changed. Nothing here
needs the Lean work: every report is about linksem's (or Lem's) own code
and is reproduced with the upstream OCaml build.

## 4. How to read a report

Each report states: what is affected (`file:line` at upstream `master`
**`4464128`**, "Quote the installation path in commands", 2024-12-14), a
description, a reproducer with **verbatim** output from the unmodified
upstream build, observed vs expected (with the oracle used), impact, a
proposed remedy, and a classification: **TRUE BUG** (behaviour contrary
to linksem's own specification or to ELF/ld), **INTENDED GAP** (a missing
feature, often marked FIXME/TODO in the source), or **UNCLEAR** (a
question for you). Where a code fix is proposed, it is described in the
report; it was checked against the upstream OCaml build with the
reproducer re-run. The Lean port itself applies only the few fixes marked
"fixed" in INDEX.md (upstream behaviour that is wrong and that our use
case exercises); for everything else it mirrors upstream.

## 5. What to trust

- The upstream build used for every reproducer is `master` @ `4464128`,
  unmodified, built with `make` in `src/`. Its OCaml was generated by
  lem-lean's `lem` (a fork of Lem adding a Lean backend; its other
  backends are regression-gated against recorded outputs). Reports 03, 04,
  05, 07, 11, 12 and 16 concern hand-written OCaml (`*_wrapper.ml`,
  `ml_bindings.ml`), which Lem does not touch; the others concern `.lem`
  code as compiled by that `lem`. Reports 08 and lem/01, which are about
  Lem's own behaviour, were reproduced with upstream Lem
  (rems-project/lem `f5529b2`, 2026-03-04); the others were not
  re-generated with upstream Lem.
- Linker reproducers compare against ld: the same objects are linked by
  `ld -static` and by `main_link`, and both executables are run.
- Outputs quoted as verbatim were produced on 2026-09-29 (x86-64 Linux,
  OCaml 5.4.0, zarith, gcc 13.3.0, binutils 2.42).
- Duplicate searches against the issue tracker were NOT possible from the
  environment these drafts were written in (no network access); see
  INDEX.md. They must be done before anything is filed.
